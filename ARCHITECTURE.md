# AI Coding Tool Preview

Native Rust rewrite of [AI Coding Tool](https://github.com/zyuapp/ai-coding-tool) (Electron + React + TypeScript), checked out beside this repository as `../ai-coding-tool` for the comparison scripts. The UI uses GPUI from Zed v1.28.1 (vendored) and must look and behave like the Electron app.

## Identity
`act_core::identity` holds every name and id the app goes by: app name, bundle and Linux app id, URL scheme, terminal command, profile folders, checkout roots, update repository, phone bridge port and user agent. The packaging scripts read the same constants. The installed app takes the Electron app's name, ids, profile and checkout root, so it replaces that app and reads its data in place; it updates from this repository's releases. A source build keeps its own profile, and its first launch with an empty one copies the Electron dev profile (`act_store::import`, read only), keeping its checkout roots as the app's own.

Shared with the Electron app on purpose: the MCP server and app plugin names agents see, in-app `aicodingtool://thread/` links in messages, the phone app's `aicodingtool://pair` scheme, the phone bridge's health answer (each copy recognises the other), and git snapshot refs. The two share the profile's lock (`SingletonLock`), so only one opens it at a time. Only one copy on a machine can hold Tailscale Serve's HTTPS port 443; the other says so.

## Control path
Same as the original:
- Every interaction is an `AppCommand` (`act_core::commands`). Commands from outside the window (agents' MCP tools, paired phones and computers) pass `act_core::validation` first.
- `act_core::reduce(&mut State, Input) -> Vec<Effect>` is the only writer of workspace state.
- The reducer describes external work as `Effect` values (`act_core::effects`).
- The window's `Workspace` entity (`crates/app/src/workspace`) runs inputs through the reducer and hands effects to the host (`crates/app/src/effects`, one module per capability, as `src/host/*-effects.ts`), which answers through `Sink` with `WorkspaceEvent`s. Effects that belong to a view rather than the host come back as `workspace::Surface`. As its state changes it also asks for the reads only a poll keeps current while their panels are on screen (plan limits, pull requests), as `src/renderer/task-workspace` does.
- Views (`crates/app/src/views`) render state and dispatch commands. Besides commands they report only what they found (`ViewEvent`: a find's count, a captured shortcut) through `workspace::report`. They contain no behaviour: what they read from the host goes through `effects::window_desktop`, the counterpart of `main/window-desktop.ts` (branches, commits, commands, diff patches, attachments, message image previews, the pasteboard's files, schedules, terminal screens, and frame calls such as the terminal theme). Anything that writes or opens something is a command.

Dependencies point downward only: app → browser/devices/ui/markdown/terminal/host → engines/store → core and platform. `act_platform` depends on no other crate of the app's.

## Platforms
- Every child process starts through `act_platform::process::{command, std_command}` (a PTY takes `child_env`): the program is found on the search path the user's login shell reported (`search_path`), and the child gets that path and the app's child variables. The app never changes its own environment.
- Per-OS code sits in modules chosen once, never in scattered `cfg`s: `act_platform`'s `sys` (`unix.rs`) and `os` (`mac.rs`, `linux.rs`), and the same `mac.rs`/`linux.rs` split in `act_host::notify` and `act_host::computer_use_host`; `act_host::dock` and `act_devices::glass` have a `none` module for systems without the feature; each `act_browser` `Pages` has the same methods. Catalogues and per-OS choices in shared code match on `act_platform::Platform`.
- A Windows port adds a `windows.rs` beside each `mac.rs`/`linux.rs` (and for `sys`), and the compiler names the `Platform::Windows` arms and missing `os` items.

## Engines
- `act_core::domain::engine` is the catalogue: each `AgentEngine`'s `EngineSpec` (id, name, built-in models, default model, capabilities such as fast mode, review and sign-in). Validation, stored records, views, the host's tools and the engines all read it; wire names are the spec ids.
- `act_engines::engines::Engine` is what an engine does: its provider for a channel, readiness, updates, commands, titles, plan usage, sign-in, subagent settings. `engines::engine` maps each `AgentEngine` to its implementation; `EngineRouter` and `EngineAccessHost` go through it.
- Every engine runs the same session skeleton. `pooled_provider::PooledProvider` is each engine's `AgentProvider`: it keeps threads' sessions warm in the channel's `SessionPool`, holds runs behind archive filings, and asks the engine's `SessionEngine` only for a session key, how to open and start a session, and what it can do with one between runs (stop a process, label, archive). `session_turn::run_turn` is every session's turn lifecycle (take the turn, watch its cancellation, interrupt, give up after the grace period, settle once); an engine's `TurnSession` says how a turn begins and is interrupted. Opening failures (`OpenFailure`, `lost` for a continuation the engine no longer has), steering (`drain_steering`) and compaction status (`Compacting`) are shared, so every engine reports them the same way.
- `tools::role_limits` is what a coordinator or member may not do (change anything, start the engine's own subagents, ask native questions); each engine enforces it its own way (Claude's tool list, Codex's sandbox and features, OpenCode's permission rules).
- Adding an engine is a variant and an `EngineSpec` in core and an `Engine` in `act_engines`; the compiler names every match that must learn it (icons, tool-call descriptions).

## Shared state
The window holds one `Rc<WorkspaceState>`; the reducer changes it in place. Threads and messages are shared between versions (`act_core::shared::Shared`, copy-on-write), so snapshots (the persistence baseline, the coordination facts taken before an input) copy pointers, not threads. `Workspace::revision` moves on every change and `outline_revision` on every change but text streaming into existing messages; views key what they derive on these and keep only weak handles to the state across updates.

## Drawing
- `Root` renders the window. The sidebar, topbar, composer, transcript and find bars are cached views (`views/parts.rs`), drawn again whenever `Root` notifies, so a scroll lays out and paints only its own part. A change only the transcript shows calls `Root::redraw_transcript` rather than `cx.notify`.
- Streaming: text streaming into the thread on screen (`Surface::Streamed`) redraws only the transcript and find bars; into a thread off screen, nothing. The sidebar model and the transcript's thread names wait for `outline_revision`.
- Live views (`act_ui::components::live`) redraw alone while the rest of the window replays its last frame. Spinners and text sweeps step through `stepped_progress`, waking the window once per step; a caret blinks the same way. An idle window draws no frames.
- The sidebar lays out only the rows near the visible part of each list (`content-visibility: auto`), from a model kept until the state changes. The transcript is a `gpui::List` whose rows not yet measured count at an estimate.
- Long messages (`act_markdown::chunk`, from 12k characters) are drawn in groups of top-level blocks. A group remembers its height per width and is built and laid out only while on screen; elsewhere it is a box of its known height, or of an estimate (its last height reflowed, or its text's bulk) while a few groups a frame are measured off screen. The list keeps the reading place as estimates give way to heights and across resizes: groups offer themselves as scroll anchors (`Window::offer_scroll_anchor`) and report heights that differ from their box (`Window::list_item_resized`).

## Vendored crates
`vendor/zed` holds Zed's GPUI crates at tag v1.28.1 (commit e8bc16ace), with each manifest standalone (Zed's workspace settings written in), taken as path dependencies; `vendor/taffy` is patched in through `[patch.crates-io]`. `scripts/test-vendor.sh [taffy|gpui|platform]` runs their tests with the features the app builds them with; the tests read fonts from `vendor/assets`.

`vendor/zed/gpui` and its platform crates have additions:
- Page zoom (`gpui::set_page_zoom`, `Window::set_page_zoom`): layout pixels map to `zoom` window points, as Chromium page zoom does. Border widths snap to whole pixels at the zoom (`snap_border_width`).
- Text as Chromium sets it: letter spacing (`FontFeatures::tracking`); line heights floor to the 1/64px layout unit and baselines sit where Chromium puts them (`line_baseline`, `line_height_normal`); line breaks as Blink finds them (`break_opportunities`); `text_indent`; `LineWrapper::truncate_line` keeps the lines it shaped and cuts at the layout unit; a text layout remembers the inherited colour and decorations it was shaped with, so hover, press and focus styles recolour it at paint. Underlines can be dotted or dashed and sit at a set distance below the baseline (`UnderlineStyle::line`, `offset`; `text_decoration_dotted`, `text_underline_offset`). macOS picks system and installed faces by weight as Chromium does.
- Layout: lengths and centred flex offsets truncate to the 1/64px layout unit; boxes snap where they land, from the root's position (`snap_root_at`, `snap_origin`); `Window::unrounded_layout_origin` gives where layout placed a node before rounding, so a subtree laid out on its own snaps as it would inside the layout; a scroller's overflow is measured before rounding (`with_whole_pixel_max` rounds its extent).
- Lists: rows not yet measured count at an estimate (`ListState::splice_estimated`, `remeasure_items`); `whole_pixel_items` stacks rows by rounded heights; `bounds_for_item` includes the top padding; scroll anchoring as a browser does it (`offer_scroll_anchor`, `list_item_resized`): a list lays its items out again within the frame, at most three times, when a shown item's height changed or its anchor moved.
- Live views (`AnyView::cached(..).live()`): notifying one does not dirty its ancestors; cached views around it replay their last frame. Each frame records its cached views (`Frame::views`); the view cache key includes the fade mask, opacity and paint transform.
- Transitions (`InteractiveElement::transition`, `gpui::Transition`): an element with an id eases its fill, border, text colour, opacity, transform and underline colour toward each new value its style takes (hover, press, focus or its own), each property on its own timing (`only`, `and`), asking for frames only while one runs. `enter` eases an element in from a start style when it first appears, as a from-only `@keyframes`. `act_ui::style::touch()` is the page's `--touch-time`/`--touch-ease`.
- Transforms (`Styled::transform`, `ElementTransform`): scale about the centre, translate, and (for glyphs and SVGs) rotate, at paint, as CSS `transform` does: `Window::paint_transform` maps every primitive, content mask, fade mask, hitbox and accessibility bound on the CPU before the scene, so both renderers draw it; hit testing uses the transform last painted. `Window::layout_content_mask` is the mask in layout space, for culling.
- Paint: backdrop filters (`backdrop_filter`, `BackdropFilter`: blur, saturate, brightness) in both renderers, with regions they read as a flat colour or replace (`hide_from_backdrops`, `replace_under_backdrops`, `with_backdrop_root`, `backdrop_ground`); edge fades (`edge_fade`, `FadeMask`) as CSS `mask-image`; radial gradients and gradients over a colour (`radial_gradient`, `over_color`); shadows as Chromium layers them; SVG strokes a device pixel wide or thinner draw as hairlines. On macOS colours blend in the display's colour space (`gpui_apple::display_color`).
- Accessibility (`accessible`, `accessible_name`, `Window::push_access_node`, `with_access_node`): a Chromium-like tree (`gpui::accessibility`) added to upstream's AccessKit tree and served by its adapters (VoiceOver on macOS, AT-SPI on Linux). On macOS a hit test off pressable elements answers the window; on Linux the tree's root follows the window's bounds. After an assistive press, hover follows the real pointer again.
- Keyboard focus as a browser has it: clickable elements are Tab stops (`skip_tab_stop` opts out), the focus ring shows only for keyboard focus (`focus_visible`), `tab_order` groups, `inert`, `focus_trap`; Enter presses on key down and Space on key up; `keep_focus_on_click`.
- Hover: an element that stops being drawn while hovered calls its `on_hover` with `false`, as a browser fires `mouseleave` when it removes one from under the pointer.
- macOS: a zoomed window reports `WindowBounds::Maximized`; mouse moves reach windows as AppKit routes them; `GPUI_DRAW_OCCLUDED=1` keeps covered windows drawing, paced by the display, for background screenshots.
- Linux: the `gpui_wgpu` renderer has the Metal renderer's backdrop passes (hidden, holes, replaced) and draws text greyscale; on X11 a window keeps its focus while an embedded child window holds the keyboard.
- Linux fonts: `.SystemUIFont` is Chromium's Linux `sans-serif` (Arial or a metric-compatible face, else fontconfig's sans-serif), and the generic names `sans-serif`, `serif` and `monospace` resolve through fontconfig.

`vendor/taffy` is taffy 0.15.0: a `flex: none` item with a negative margin keeps its size in intrinsic sizing; centred flex offsets truncate to a set layout unit (`set_layout_unit`); nodes with `snap_origin` sit on whole pixels, and a root rounds from where it is placed (`round_layout_from`).

## Linux web views
GTK runs on GPUI's main thread (`act_browser::linux::gtk_loop`). Hidden pages (Mermaid, screenshot marks) live in a GTK offscreen window (`act_browser::hidden`). On X11, browser tabs and visuals are WebKitGTK views in X windows inside GPUI's (`act_browser::linux::embed`); on Wayland they render in GTK offscreen windows whose frames the app paints and to which it hands pointer and keys (`act_browser::linux::offscreen`), with `<select>` lists shown as the app's own menus. GTK's accessibility bridge runs only while a page is open.

## Building and checks
Shaders compile at runtime (`runtime_shaders`), so no Metal toolchain is needed.
- `cargo run -p ai-coding-tool`; `ACT_PROFILE_DIR` picks a profile, `ACT_WINDOW_SIZE=WxH` the window size.
- `cargo test --workspace`, and `scripts/test-vendor.sh` for the vendored crates.
- Build time: a crate that reads or writes a type through `serde_json` compiles that type's whole serde tree again. `crates/core/src/json.rs` gives the largest (`AppCommand`, `WorkspaceEvent`, `WorkspaceInput`, `WorkspaceState`, `Thread`, the phone views) `from_json` and `to_json`, compiled once in core; other crates call those. `cargo llvm-lines` shows what a crate compiles. The app is a library under a one-line `main.rs`, so it compiles while the crates under it are still generating code.
- `scripts/reducer-diff/run.sh` fuzzes the reducer against the TypeScript one; `scripts/command-diff/run.sh` compares command validation with it.
- `scripts/package-mac.sh` builds the `.app`, signed with `MAC_SIGN_IDENTITY` or ad hoc; `scripts/package-linux.sh [x86_64|aarch64]` the Linux tarball (and AppImage when `appimagetool` is on PATH), in Docker when not on Linux.
- `scripts/profile.sh <dir>` copies the Electron dev profile (or `ELECTRON_PROFILE`) for `ACT_PROFILE_DIR`; `scripts/shot.sh <process-name-or-pid> out.png` screenshots a window. Compare against the Electron dev app (`npm start` in `../ai-coding-tool`).
- `.github/workflows/release.yml` builds, signs, notarizes and publishes a release with the update feeds `act_host::updates` reads; `scripts/release-feed.sh` writes those feeds. Start it from main (`gh workflow run release.yml --ref main`) after bumping the version: only runs on main keep their Cargo cache (`scripts/cargo-cache.sh`) for the next release.
- `python3 -I scripts/third-party-notices.py` regenerates `assets/legal/THIRD-PARTY-NOTICES.txt` from `Cargo.lock` (`--check` fails when it is stale); `--cua-driver <trycua/cua checkout>` regenerates the Linux Cua Driver's crate report. `assets/legal/linux` ships only in the Linux packages. The in-app reader lists the files in `assets/legal` (`crates/app/src/licenses.rs`).
